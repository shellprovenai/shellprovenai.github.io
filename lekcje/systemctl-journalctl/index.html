systemctl and journalctl for people who only need five commands: status, logs, follow, enable

The five systemd commands you actually need, on a real systemd running in a container: check a service with systemctl status, find out why a service failed with journalctl -u, read logs since boot or the last few minutes, follow logs live, and the start vs enable trap (enable --now does both).

# 5. start vs enable
$ systemctl is-enabled hello-app
disabled
$ systemctl stop hello-app && systemctl enable hello-app
Created symlink '/etc/systemd/system/multi-user.target.wants/hello-app.service' → '/etc/systemd/system/hello-app.service'.
$ systemctl is-active hello-app
inactive
$ systemctl enable --now hello-app && systemctl is-active hello-app && systemctl is-enabled hello-app
active
enabled

PRACTICE — lesson 15: why did the service fail?
-----------------------------------------------
/work/journal is the systemd journal copied from server web1 (it
has two boots), and /work/rootfs is the disk of that server. No
systemd runs in this container, so read the journal with
journalctl -D /work/journal ... and change the server's units with
systemctl --root=/work/rootfs ...

1. backup.service failed during the LAST boot of web1. Write the
   full path of the program it could not find to /work/missing.txt
   (only the path, like /usr/bin/example).
2. The program really is /usr/local/sbin/backup-run on that disk.
   Fix /work/rootfs/etc/systemd/system/backup.service and make sure
   it will start at every boot of web1. Leave nginx.service alone.

Check: sh /practice/check.sh     Answer: /practice/solution.md

Inside, sh check.sh tells you when you are done. Stuck? solution.md — but try first.
